# Purpose

This document defines the official contribution guidelines of Limoxel.

Its purpose is to establish a consistent, transparent, and engineering-focused process for contributing to the project while preserving the quality, stability, security, and long-term integrity of the platform.

Limoxel welcomes community contributions and values every genuine effort to improve the project. However, every contribution must satisfy the engineering standards, architectural principles, and governance policies established by the project.

As a Core Foundation Document, this document serves as the canonical source of truth for contributing to Limoxel.

---

# Contribution Philosophy

Limoxel is built on the belief that high-quality software is the result of thoughtful engineering, disciplined collaboration, and continuous learning.

Every contribution should strengthen the platform, improve engineering quality, and move Limoxel closer to its long-term vision.

Community participation is encouraged, but engineering excellence always takes precedence over contribution volume.

---

# Contribution Principles

## 1. Quality Before Quantity

Every contribution should improve Limoxel.

A single well-designed contribution provides significantly more value than numerous rushed or incomplete changes.

Engineering quality will always be prioritized over the number of accepted contributions.

---

## 2. Architecture Before Code

Significant changes should begin with understanding rather than implementation.

Contributors are expected to understand the relevant architecture, engineering principles, and design decisions before proposing modifications.

Code should follow architecture—not define it.

---

## 3. Respect the Foundation

Every contribution must remain consistent with Limoxel's established:

- Mission Statement
- Vision Statement
- Long-Term North Star
- Engineering Principles
- Architecture Principles
- Code Quality Standards
- API Philosophy
- Plugin Philosophy
- Repository Governance

No contribution should conflict with the project's Core Foundation Documents.

---

## 4. Contribution Readiness

Before submitting a contribution, contributors are expected to:

- Understand the problem being solved.
- Study the relevant documentation.
- Understand the affected architecture.
- Follow established engineering standards.
- Verify that the proposed implementation aligns with the project's philosophy.

Contributions made without sufficient understanding of the affected system are unlikely to be accepted.

---

## 5. Documentation Travels With Code

Documentation is part of the implementation.

New features, public APIs, architectural changes, behavioral changes, and significant engineering decisions should include appropriate documentation.

Incomplete documentation should be treated as incomplete engineering work.

---

## 6. Evidence-Based Engineering

Technical decisions should be supported by:

- Engineering reasoning
- Architectural consistency
- Verified implementation
- Real-world use cases
- Performance evidence where applicable

Engineering decisions should not rely solely on personal preference.

---

## 7. Small and Focused Contributions

Contributions should address one clearly defined engineering objective.

Smaller, focused pull requests are easier to review, understand, test, and maintain than large collections of unrelated changes.

---

## 8. Constructive Reviews

Code reviews exist to improve both the software and the contributor.

Reviews should remain respectful, objective, educational, and focused on the implementation rather than the individual.

---

## 9. Preserve Compatibility

Contributors should preserve backward compatibility whenever reasonably possible.

Breaking changes require clear technical justification, migration guidance, and explicit approval before becoming part of the official project.

---

## 10. Testing Is Expected

Every meaningful contribution should include appropriate validation.

Bug fixes should include regression tests whenever practical.

New capabilities should include suitable automated tests that demonstrate correctness and preserve long-term reliability.

---

## 11. Think Long Term

Engineering decisions should be evaluated based on their long-term value rather than immediate convenience.

Contributors should ask:

> **Will this still be a good engineering decision several years from now?**

If not, the solution should be reconsidered.

---

## 12. Community Ownership Through Collaboration

Ideas are evaluated on engineering merit rather than contributor experience, popularity, or reputation.

Every contributor has the opportunity to improve Limoxel through thoughtful engineering and respectful collaboration.

---

## 13. Transparency

Engineering discussions, design proposals, architectural decisions, and review outcomes should remain transparent whenever practical.

Transparency strengthens trust and improves engineering quality.

---

## 14. Learning Environment

Limoxel should help engineers grow.

Questions are encouraged.

Knowledge should be shared.

Reviews should educate as well as evaluate.

The contribution process exists not only to improve the codebase but also to cultivate stronger engineers.

---

## 15. Sustainable Engineering

Engineering work should improve the project without creating unnecessary long-term maintenance burden.

Long-term maintainability should always take precedence over rapid implementation.

---

## 16. Recognition

Every meaningful contribution deserves appreciation.

Whether a contributor improves:

- Code
- Documentation
- Tests
- Design
- Performance
- Security
- Reviews
- Bug reports
- Discussions

their effort strengthens the project and is genuinely valued.

Contribution acceptance is independent of appreciation.

---

## 17. Repository Governance

The official Limoxel repository is owned and governed by **Raj Joshi**.

Repository ownership includes responsibility for:

- Engineering direction
- Architectural integrity
- Repository governance
- Release management
- Documentation
- Community stewardship
- Long-term project sustainability

The responsibility of protecting the project cannot be delegated without an explicit governance decision.

---

## 18. Review Before Merge

Every contribution undergoes engineering review before becoming part of the official repository.

The review verifies that the proposed changes:

- Preserve stability.
- Maintain architectural integrity.
- Follow engineering standards.
- Comply with coding standards.
- Protect security.
- Preserve compatibility where applicable.
- Improve the long-term quality of the project.

Submission of a contribution does **not** guarantee acceptance.

> Contributors who are uncertain about a feature, architectural change, or major implementation are encouraged to discuss their ideas before investing significant development effort. Early discussions help align proposals with the project's long-term vision, reduce unnecessary rework, and often lead to stronger engineering outcomes for everyone involved.

Only reviewed and approved contributions become part of Limoxel.

---

## 19. Protection of Critical Components

Changes affecting critical infrastructure—including the core engine, parsers, repository analysis, knowledge graph generation, storage systems, APIs, backend services, security mechanisms, or other foundational components—receive heightened engineering review.

Contributors are expected to understand these systems before proposing modifications.

Changes that could compromise platform stability, correctness, security, architectural integrity, or long-term maintainability require a higher standard of technical justification and validation.

---

## 20. Protect the Official Repository

The stability and integrity of Limoxel take precedence over accepting contributions.

Changes that intentionally or unintentionally introduce instability, architectural degradation, security risks, unnecessary complexity, or regression will not be merged into the official repository.

Good-faith mistakes are treated respectfully as learning opportunities, but protecting the quality of the official project remains the highest priority.

---

## 21. Final Approval Authority

Community contributions are welcomed and genuinely appreciated.

However, the official repository represents the canonical implementation of Limoxel.

Final authority to approve, request revisions, defer, or reject any contribution remains with the repository owner.

This responsibility exists to preserve the long-term quality, stability, consistency, and engineering integrity of the project.

- Code contributions
- Documentation
- Bug fixes
- Performance improvements
- Refactoring
- Architecture proposals
- Plugin development
- Tests
- Design discussions
- Community contributions

Every contribution to the official repository is expected to comply with these guidelines.

# Foundational Principles

The Contribution Guidelines establish the following permanent commitments.

- Welcome and appreciate community contributions.
- Protect engineering quality above contribution volume.
- Require understanding before modification.
- Review every contribution before acceptance.
- Preserve architectural integrity.
- Encourage learning and respectful collaboration.
- Recognize every meaningful contribution.
- Protect the stability and reliability of the official repository.
- Maintain repository governance under the repository owner.
- Build a sustainable engineering community focused on long-term excellence.

# Applicability

The principles defined in this document apply throughout the entire lifecycle of Limoxel and are expected to guide:

- Community contributions
- Pull requests
- Engineering reviews
- Documentation updates
- Plugin submissions
- Architecture proposals
- Repository governance
- Long-term community growth

The success of Limoxel's community should be measured not by the number of contributions received, but by the quality, integrity, and lasting engineering value of the contributions accepted.

# Change Policy

The Contribution Guidelines represent the enduring governance philosophy of Limoxel and are intended to remain stable throughout the lifetime of the project.

Changes to this document should be exceptionally rare and only occur when the project's governance philosophy fundamentally evolves.

Any modification requires explicit approval from the repository owner.
